# Path Cloud Sync — этап 1, техническая подготовка

Дата: 31 октября 2026. Статус: протестированный прототип ядра и миграция сервера. В Windows RC6 синхронизация НЕ включена, установщик не заменён. Личные данные не отправлялись.

## Аудит совместимости
- ID задач и проектов уже постоянные; генерация новых ID при синхронизации не нужна.
- Задачи Today и задачи внутри Projects имеют разные контейнеры, но общее пространство ID. Их нужно передавать одним согласованным снимком вместе с проектами и зависимостями.
- Существующий PathRepository атомарно сохраняет локальный checkpoint. Очередь синхронизации при подключении к приложению должна фиксироваться вместе с локальным изменением либо восстанавливаться сравнением сохранённого снимка с подтверждённой базой. Отдельная запись очереди после сохранения без восстановления неприемлема.
- Аккаунты уже имеют раздельные локальные профили. Очередь дополнительно привязана к ownerId, открытие чужой очереди запрещено.
- Локальное восстановление профиля в RC6 не означает наличие действующего серверного access token. Транспорт требует проверенную серверную сессию; токены должны оставаться в main-процессе. Текущий OAuth-адаптер нужно расширить хранением access token в памяти, сроком действия и обновлением до подключения транспорта. Хранить токен в renderer нельзя.
- Calendar, Canvas, Notes и Progress ссылаются на задачи. При применении удалений из облака потребуется проверка локальных ссылок и восстановление/подтверждение конфликтов, прежде чем включать автообмен в UI. Изображения и остальные разделы пока не включены.
- Supabase административный доступ в этой сессии отсутствует. Схема в живом проекте не установлена.

## Минимальная первая модель
Личный снимок {schema:1, homeTasks, projects}, максимум 2 MiB. Существующие поля проектов и задач сохраняются. Notes/Journal, Calendar, Canvas, Sport и настройки не выбираются из общего состояния для отправки. Текст, уже записанный пользователем в задаче или описании проекта, является частью этих данных.

Один серверный номер ревизии на аккаунт. Запись разрешена только при совпадении ожидаемой ревизии (compare-and-swap). Каждая попытка имеет постоянный UUID; повтор после потери ответа не создаёт повторную ревизию. История хранит снимки, включая предыдущее состояние удалённых объектов.

При независимых одновременных правках может возникнуть конфликт целого снимка. Автоматического слияния и совместного редактирования в этом этапе нет. Обе версии сохраняются; выбор требует завершённой резервной копии. Новый компьютер со старыми записями не восстанавливает молча уже удалённые облачные данные.

## Что реализовано
- replica.cjs: проверка структуры и ID, постоянная очередь, восстановление после перезапуска, повтор операций, обработка ACK, сохранение правок во время запроса, обнаружение конфликтов, явное разрешение с резервной копией. fileStore — отдельный тестовый файловый адаптер, не подключён к пользовательскому PathRepository.
- transport.cjs: ограниченный RPC-транспорт для фиксированного Supabase, проверенный токен перед запросом, запрет redirect, timeout. Не запускается автоматически, не читает данные приложения.
- 001_personal_tasks_projects.sql: отдельная закрытая схема, heads/revisions/testers, RLS и отсутствие прямых прав на таблицы; два RPC с проверкой auth.uid(), конкретного OAuth client_id и списка тестировщиков. Owner берётся из проверенного JWT, а не из тела запроса. SECURITY DEFINER с фиксированным search_path и явным owner-фильтром.
- config.json: enabled=false.
- enable-test-user.sql: отдельный шаблон допуска тестировщика. Не выполнялся.
- project-control/check-cloud-sync.cjs и sync-tools/package*.json: воспроизводимый набор проверок.

## Проверено
Команда: npm ci --prefix project-control/sync-tools; node project-control/check-cloud-sync.cjs.

PASS на PostgreSQL в PGlite (локальный WASM-движок, не mock SQL): выполнение миграции; owner/client/tester ограничения; запрет anon и прямого чтения таблиц; CAS; повтор операции после новых ревизий; отказ повторному UUID с другим содержимым; конфликт двух независимых реплик; резервная копия до разрешения; история удалений; отказ несовместимой структуре и повторяющимся ID.
PASS локально: очередь на диске после перезапуска и потери ACK, сохранение новых правок во время запроса, отказ диска без изменения памяти, изоляция ownerId, исключение частных разделов из проекции, защита от восстановления удалений при первом подключении старого устройства.
PASS транспорт: фиксированный endpoint, заголовки и запрет отправки без токена (HTTP имитируется).

НЕ проверено: живой Supabase, настоящий JWT/PostgREST, сеть между компьютерами, Windows UI и применение cloud pull в локальные связанные разделы. Готовность всей Cloud Sync не заявляется.

## Следующие шаги и критерии готовности
1. Установить приложенный SQL в Path Accounts Test. Пока никто не включён в testers и данные не загружаются.
2. Добавить отдельного тестового пользователя по его Authentication User UUID, НЕ по OAuth Client ID. Проверить реальные read/write и отказ другому пользователю.
3. Подключить ядро к Windows за явным переключателем в Profile: подтверждение отправляемых разделов, статус pending/saved/error/conflict, безопасный flush редакторов, проверка полного локального состояния перед pull, очередь без потерь при закрытии. При импорте/Undo также учитывать очередь.
4. Выпустить приватную тестовую сборку и проверить два устройства: изменение на A видно на B; офлайн-правки доходят после подключения; одновременные правки не теряются; удаление не воскресает; повтор/перезапуск не создаёт дубликатов; другой аккаунт ничего не видит.
5. Только после этого подключать другие разделы и вложения. До публичного запуска нужны политика хранения истории/лимиты, резервное копирование сервера и восстановление из неё. История ревизий сейчас не заменяет отдельную резервную копию базы.

## Что сделать сейчас в Supabase
Открыть Path Accounts Test → SQL Editor → New query. Скопировать весь 001_personal_tasks_projects.sql и нажать Run. Ожидается Success (обычно No rows returned). Это создаёт только новую схему/таблицы/функции; существующие пользовательские записи не переносятся и не заменяются. Секретные ключи или пароль базы присылать не нужно.
