# Calendar/Habits — серверный протокол и тестовое подключение

31 октября 2026. Код подготовлен, в установленной RC13 не включён.

## Реализовано

- `002_calendar_habits.sql`: отдельные таблицы снимков и истории, RPC чтения/записи версии 2, RLS и отсутствие прямого клиентского доступа. Доступ проверяет аккаунт, OAuth client_id и два списка тестеров.
- Контроль ожидаемой ревизии, уникальный ID операции и возврат исходного подтверждения при повторной отправке. Проверяются структура снимка, лимит 2 МиБ, ID, связи задач, зависимости, события, время, серии, отмены и записи привычек. Sport пока блокируется.
- Переход требует совпадения ревизии и задач со старым облачным снимком. Само чтение или установка миграции не переводит аккаунт на новую версию.
- Операции v1/v2 одного аккаунта используют общую транзакционную блокировку. После активации v2 RPC старой версии возвращают `SYNC_CLIENT_UPGRADE_REQUIRED`. Исходные таблицы и история v1 сохраняются.
- `transport-v2.cjs`: только заданный сервер, проверенный токен от вызывающего кода, запрет перенаправлений, тайм-аут и проверка ответа.
- `session-v2.cjs`: явная активация/первое принятие облачной версии, резервная копия до изменений, очередь повторной отправки, журнал применения, восстановление после сбоя, сохранение новых правок во время запроса и явный выбор версии при конфликте.
- `checkpoint-adapter.cjs`: применение через существующее хранилище приложения, проверка незавершённого редактирования, сохранение локальных Notes/Canvas/settings и запрет удаления связанных записей.

Все новые клиентские компоненты требуют явного `testMode: true`. Они не подключены к запуску RC13, её кнопкам или автосинхронизации.

## Проверки

Прошли:

- 13 серверных сценариев на PostgreSQL через PGlite: повторное выполнение миграции, отсутствие автоматического допуска, защита старой версии, CAS, повторные запросы, разделение аккаунтов, права, некорректные снимки и зависимости. Два тестовых клиента также обменялись изменениями через эти SQL RPC; потерянное подтверждение повторено без новой записи.
- 16 сценариев тестовой сессии: активация, копии, первоначальное принятие облачных данных, объединение двух клиентов, конфликт, выбор версии, офлайн, потерянный ответ, перезапуск, правки во время запроса, ошибка копирования, сбои до/после применения, расхождение при восстановлении, занятый редактор, переполнение хранилища, ссылки из локальных разделов, ошибка журнала, токен и адрес сервера.
- 19 проверок объединения Calendar/Habits из предыдущего этапа.
- Повторные регрессионные проверки текущего облачного протокола и его применения.

Авторизация в PGlite моделируется тестовыми claims. Реальный OAuth, сеть Supabase, параллельные транзакции на отдельном сервере и два Windows-компьютера пока не проверены.

## Что делать пользователю сейчас

Переустановка и запуск SQL сейчас не нужны. Ваш сервер, установленная RC13 и публичный сайт не менялись.

Следующий этап — подключить подготовленные компоненты к отдельной Windows-сборке: проверка личности в основном процессе, элементы интерфейса тестового режима, понятный отказ для старых клиентов и обработка восстановления. Затем провести отдельный переход тестового аккаунта и общую проверку на двух компьютерах.

## Порядок будущего тестового развёртывания

1. Сохранить полные локальные копии обоих устройств и проверить, что текущие задачи синхронизированы. Решить перенос событий без явного часового пояса и Sport-зависимостей; сейчас они блокируют новый снимок.
2. Проверить миграцию 002 после 001 на отдельном проекте. В момент применения не должно быть незавершённых записей старого протокола. Миграция не содержит автоматического добавления тестовых пользователей.
3. Подготовить и проверить новую сборку на обоих устройствах. Только затем отдельно добавить нужный аккаунт в список v2-тестеров и выполнить явную активацию с резервной копией.
4. После активации не использовать RC13 для этого аккаунта: сервер отклонит её облачные операции. Не удалять v2-снимок ради включения старого клиента и не выполнять 001 повторно — это откроет путь к расходящимся версиям.
5. При откате сначала сохранить обе истории и согласовать актуальные задачи. Автоматического отката сервера, который мог бы потерять события/привычки, здесь нет.

Исходники и инструкции сохранены; готового нового установщика на этом этапе нет.
