## Расхождения, важные для обмена

1. После импорта и перезапуска desktop проставил тестовому дедлайну без времени поле `tzid: Europe/Warsaw`. Сама дата и состав событий сохранились. Для обмена нужна единая семантика календарной даты, чтобы автоматическое добавление зоны не считалось пользовательской правкой.
2. Тестовый полный протокол v3 исключает корневое поле `sportsLibrary` из передаваемого документа. Проверено с пользовательским упражнением, избранным и недавними упражнениями. Формат полного файла desktop эти данные сохраняет. Перед обменом нужно определить правила объединения библиотеки и выбрать, переносить ли недавние упражнения между устройствами.
3. На завершённой записи Sport v4 воспроизведено различие валидаторов. Приложение принимает запись, а упакованный валидатор обмена v3 возвращает `Sport v4 contract is unavailable.` В его окружение загружаются только `timezone.js` и `storage.js`. Успех прежних тестов v3 на старых записях не покрывает этот случай.
4. Обычный мобильный профиль, режим совместимой копии и desktop используют разные пути сохранения. Для автоматического обмена на телефоне нужен клиент с общей базовой ревизией, сохранением ожидающих операций и обработкой конфликтов. Полный импорт заменяет состояние и сам по себе не решает задачу объединения.

### Повторная проверка дедлайнов

После исправления обе версии сохраняют новый дедлайн как календарную дату с нулевыми `hour` и `duration`. При переводе события в дедлайн или переносе дедлайна на другую дату убираются `tzid`, `fold`, `start_at` и `end_at`. Импорт, перезапуск и переименование сохраняют прежние поля старых записей.

После сборки обеих версий команда `node project-control/check-deadline-roundtrip.cjs` проверяет перенос через совместимую копию. Компьютер создаёт дедлайн на 4 ноября 2018 года в часовом поясе Сан-Паулу, где в этот день часы пропустили полночь. Мобильный адаптер в часовом поясе Токио открывает ту же дату и меняет название. Компьютер импортирует результат и повторно экспортирует его после перезапуска. Тест сверяет все поля события. Сохранение в обычном мобильном профиле и смену типа события проверяет `mobile/tests/calendar-model.test.mjs`.

## Проверки

Команды запускались из корня проекта. Для браузерных проверок использовался локальный Chromium, для SQL — зависимости из lock-файла `project-control/sync-tools`.

Первый практический этап синхронизации — обмен одним обычным событием Calendar и отметкой привычки между двумя изолированными клиентами. Критерии приёмки — обе независимые правки сохраняются, конфликт одной записи виден после перезапуска, повтор после обрыва связи не создаёт копию. Для включения Sport в этот сценарий сначала нужны общий валидатор v4 и поддержка библиотеки в формате обмена.
