# Path Mobile / desktop: Functional Alpha contract

Audited desktop source is read-only. This stage continues mobile baseline `3d80a0776b4519e0ebabdbd0088e15e0c26c1d64`. No desktop storage, account, export or production data was opened. Source references below are paths relative to the repository root, not runtime imports.

## Boundaries and round-trip

`mobile/desktop-adapter.mjs` accepts the **object envelope** confirmed by `privacy-export.js:pathBackupState` and `storage.js:pathCheckpointEncode/pathCheckpointDecode`: `{format:'path-checkpoint',version:2,state,...}`. It produces a versioned **staging document**, not an active mobile repository. `restoreDesktopCheckpoint` reconstructs an equivalent envelope. It neither writes storage nor appends/merges entities. Repeating staging/re-export is idempotent; the tests compare all JSON data, IDs, relationships, root extensions, envelope extensions, rich content and attachment asset references.

This is a lossless inspection boundary, **not a completed desktop → live mobile importer**. Desktop `createdAt` can be numeric; mobile's old root contract uses ISO. Habits can have weekly/count/duration/sport rules that mobile cannot activate. Desktop task IDs can be scoped to projects, while the older mobile `mainTasks` references contain only an ID. These require an explicit activation/merge contract before enabling import. Unknown root collections are retained as opaque values; the mobile UI refuses writes to an unsupported collection shape.

Checkpoint `imageCodec` 1/2, `imageAssets` and `{pathImageAsset:index}` values are kept intact. The staging adapter does **not** decode, fetch, display, upload, or deduplicate payloads. Asset resolution is a separate future adapter. No promise is made that staging a checkpoint makes its attachments usable in mobile. JSON trees reject unsafe keys, cycles, non-JSON objects, depth >64, and >250,000 visited values. Duplicate IDs within a collection or one project's tasks are rejected; collisions between different scopes are not renamed. No untrusted file picker/import UI is exposed.

All supported mobile edits patch the original record in a cloned candidate. Unknown properties are retained. Atomic persistence validates the candidate and writes under Web Locks; memory/revision advance only after `localStorage.setItem` succeeds. A stale tab must explicitly refresh and review its retained draft. A schema/Undo version the app cannot understand fails closed without replacing stored bytes.

## Field map

“Same / reversible” below means the field is copied verbatim by staging/re-export. Runtime support is described separately; it is not a claim of universal mobile editing. Every unlisted property at every level remains opaque and reversible through staging. No unknown property is silently discarded or interpreted as an account identifier.

Today reads canonical task entries. `mainTasks[date]` is a reference, not a clone. Moving/deleting a selected task clears the obsolete reference. Calendar project deadlines have ephemeral IDs `task-deadline:<taskId>` and open the shared nested-task editor. They are **never written to `events`**; their completed appearance reflects the task, not a new desktop deadline completion enum. Existing linked Calendar records remain protected. Ambiguous cross-scope task IDs are not shown as duplicate Today controls; inspect them within the source project, read-only. Resolving scoped identities is required before runtime desktop activation.

Project progress follows `original.html:projectPercent`: `round(done task count / all task count * 100)`, empty project = 0. Project state and its tasks are independent: completing tasks does not silently rewrite project state.

## Progress dates and formulas

- Period = Today, Monday through current local date, or first of current month through today. All boundaries use the device's civil calendar; language changes labels only.
- Completed tasks = canonical root + nested tasks currently done **and** with `completedAt` falling within the period in device local time. Main references and derived Calendar cards add no extra count. Reopening clears completion. Untimestamped legacy done tasks are excluded rather than assigned invented dates. Changing device time zone can move an instant between civil days.
- Habit numerator = eligible completed habit/date pairs in period; denominator = eligible habit/date pairs, including an incomplete current day. Future days are not included. Dated availability/exceptions/schedules apply. This is a period-to-date completion ratio, not the desktop weekly-target metric.
- Completed workouts = distinct record IDs with a valid endedAt in period. Planned events and active sessions do not count.
- Project percentages are current lifetime task progress, shown independently of the selected period; formula above. No estimated minutes are presented as actual focus time, and no random charts/achievements are generated.

## Migration, backup and future sync proposal

Schema 4 → 5 adds only absent collections and mobile motion preferences. Versions 1–4 migrate in memory without rewriting stored bytes until the next successful user write; repeating migration changes nothing. IDs, event intervals, habit history and unknown fields stay intact. `mobileProjectUndo` version 1 retains the exact removed task, project ID, insertion position and affected main references. It is a mobile extension, not a desktop operation log.

Settings export uses a distinct `{format:'path-mobile-backup',version:1,schemaVersion:5,exportedAt,state}` JSON wrapper. It is not labelled a desktop export. There is no UI import/merge; validated recovery tooling and conflict review must precede that feature. A source archive or Git bundle contains code/history, **not browser localStorage**.

Future proposal, not implemented:

1. Offline operation envelope: stable operation UUID, entity scope/ID, client ID, base revision, minimal patch and civil/instant semantics; persist outbox atomically with domain change. Never infer success from connectivity alone.
2. Idempotency: server records applied operation IDs; replay returns prior result. Import uses provenance plus scoped stable IDs and explicit preview, not append-every-time or random remapping.
3. Deletes: durable tombstones with revision and retention; undo/restore carries provenance. Avoid resurrecting a remotely deleted item from an older tab/backup.
4. Conflicts: compare base revision; show both versions for text/schedule/link conflicts. No unconditional last-writer-wins for rich documents, recurrence exceptions, active sessions or completed snapshots.
5. Attachments: hash-addressed immutable blobs, explicit upload state and size/type checks, referenced separately from document edits; preserve missing assets and defer rendering instead of silently removing them.
6. Personal/Shared: add server-validated ownership and workspace scope only with real membership. Do not fabricate account IDs now. Keep private journal data private; shared views must be permission-filtered by the server.
7. ACL: authorization on every server mutation/read; offline drafts cannot grant access. Define revocation, export/import and attachment permissions before enabling shared sync.

Review these contracts with desktop owners before enabling activation or sync. No desktop change is required or made for this isolated Alpha; runtime import, shared editing, recurrence and complete program/Gantt support remain separate work.
